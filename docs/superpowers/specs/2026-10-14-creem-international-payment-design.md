## 2. Phạm vi

**Làm:**
- Cổng thứ hai `creem` bên cạnh `payos`: khách chọn trả bằng thẻ, loại tiền USD, trang thanh toán do Creem lo (thẻ, Apple Pay, Google Pay; Creem là bên bán lại, merchant of record: tính, thu và nộp thuế).
- Server: `CreemProvider`, đổi `PaymentProvider`, chọn cổng theo loại tiền, webhook Creem, xử lý hoàn tiền và tranh chấp, sự kiện không khớp đơn, giữ đơn có số tiền lạ, cảnh báo khóa API theo cổng, thống kê Web Admin theo loại tiền.
- Web Admin: thẻ hoàn tiền theo loại đơn, thao tác rút ngắn hạn license.
- App: chọn cách trả, đơn không có mã QR (mở trình duyệt), hiển thị USD, câu merchant of record.
- Website (giá USD, cách mua), EULA 1.3, chính sách quyền riêng tư 1.2, runbook.

**Không làm (v1):** thuê bao tự gia hạn; mã giảm giá; nhiều loại tiền ngoài USD (EUR, JPY…); tự thu hồi hay tự rút ngắn license khi hoàn tiền; chạy Creem cho khách chọn VND; chia doanh thu, affiliate (Creem tính thêm 2% cho mỗi thứ); đổi luồng thanh toán PayOS (PayOS chỉ có thêm cảnh báo, §4.1); đổi token, license, hạn mức; đối soát hoàn tiền (hoàn tiền và tranh chấp chỉ đến qua webhook, §10).

## 3. Luồng tổng thể

1. App gọi `GET /v1/plans?plans=…`; server trả bảng gói (giá của các loại tiền đang bán được) và `suggested_currency`.
2. Khách chọn cách trả, nhập email, tick đồng ý. App gọi `POST /v1/checkout {plan, email, consent, license_key?, currency: "USD"}`.
3. Server tạo dòng `orders` (`provider='creem'`, `currency='USD'`), gọi Creem `POST /v1/checkouts` với `request_id = order_code`, nhận `id` và `checkout_url`, lưu `provider_ref = id`, trả `qr_code: null` và `checkout_url`.
4. App mở `checkout_url` bằng trình duyệt hệ thống (không mở trong webview), hỏi `GET /v1/orders/{code}` mỗi 5 giây trong hạn đơn, rồi thưa dần tới 24 giờ sau hạn (§5).
5. Khách trả tiền ở trang của Creem. Creem gửi webhook `checkout.completed` tới `/v1/webhooks/creem`.
6. Server kiểm chữ ký trên thân thô, rồi **hỏi lại API Creem** (`GET /v1/checkouts?checkout_id=`) để biết trạng thái thật; chỉ cấp license (`grantOrder`) và gửi email key khi phiên đã trả đủ giá, không có dấu hiệu giảm giá và dữ liệu tiền đọc được (§4.2); còn lại đơn bị giữ và người vận hành được báo. Webhook chỉ là cái cò; cron đối soát 5 phút cấp được license kể cả khi webhook mất.
7. App thấy `paid`, tự kích hoạt (đơn mới) hay `validate` (gia hạn, đổi gói), như hôm nay.

License, token, hạn mức, luật mua thêm và đổi gói **không đổi**: chúng chỉ biết gói, `expires_at`, `cycle_anchor`. Thao tác rút ngắn hạn của Web Admin chỉ trừ `expires_at` (§4.6).

## 4. Server

### 4.1 Giao diện `PaymentProvider` (`server/src/payment/provider.ts`)

Hai hàm cũ không đủ cho cổng có chữ ký ở header và không tra được theo mã đơn của ta:

```ts
export interface WebhookRequest { rawBody: string; headers: Headers }

export type WebhookEvent =
  | { kind: "payment"; orderCode: number; providerRef?: string | null;                 // cò kích hoạt cấp license
      reportUnknownOrder?: { eventType: string; eventId: string | null } }
  | { kind: "refund"; eventType: string; providerRef: string; reason: "refund" | "dispute"; full: boolean;
      eventId: string | null; refundedAmount: number | null; providerAmountPaid: number | null;
      refundStatus: string | null; providerReason: string | null }                   // hoàn tiền hay tranh chấp; tra đơn theo provider_ref
  | { kind: "unmatched"; eventType: string | null; providerRef: string | null; eventId: string | null } // đúng chữ ký, không chỉ ra đơn nào
  | { kind: "ignore" };                                                               // sự kiện không dùng: trả 200

interface PaymentProvider {
  readonly name: string;
  readonly sells?: boolean;  // false: chỉ xử lý đơn đã có, không tạo phiên mới (Creem chưa đủ mã sản phẩm)
  createCheckout(req: CheckoutRequest): Promise<CheckoutResult>; // CheckoutRequest thêm `plan`, `email`; CheckoutResult.qrCode: string | null
  verifyWebhook(req: WebhookRequest): Promise<WebhookEvent | "malformed" | null>;
  getPaymentStatus(ref: { orderCode: number; providerRef: string | null }): Promise<PaymentStatusResult>;
}
// PaymentStatus thêm "refunded". PaymentStatusResult thêm `reviewDetail?: ReviewDetail` (dữ kiện của cổng khi đơn bị giữ, §4.2).
// new PaymentProviderError(message, code?, httpStatus?, unreachable = false, jsonBody = false); isProviderAuthFailure(err).
```

- **`PaymentProviderError.jsonBody`:** thân phản hồi lỗi là JSON đúng kiểu của chính cổng (Creem: đối tượng có `trace_id` dạng chuỗi; PayOS: đối tượng có `code` dạng chuỗi). **`isProviderAuthFailure`** đúng khi HTTP 401 hay 403 **và** `jsonBody`: 401/403 của tường lửa hay CDN (HTML, JSON lạ), chuyển hướng, lỗi mạng và mọi mã khác không phải lỗi khóa.
- **`PayOSProvider`** đổi theo: `verifyWebhook` tự `JSON.parse` thân thô rồi làm như cũ (trả `{kind:"payment", orderCode}`, không `providerRef`, không `reportUnknownOrder`); `getPaymentStatus` dùng `orderCode`, bỏ qua `providerRef`. **Luồng thanh toán PayOS** (tạo link, chữ ký, ánh xạ trạng thái, luật cấp) giữ nguyên và test PayOS cũ qua nguyên vẹn (sau khi sửa chữ ký hàm). Câu "hành vi PayOS không đổi" của bản 2026-10-14 nay không còn đúng hoàn toàn; PayOS có thêm:
  - đơn PayOS lệch số tiền (`failed`, nhật ký `order_amount_mismatch`, `detail` nay có `currency`) tạo cảnh báo `order_payment_review` (§4.4). Đơn PayOS `underpaid` (khách chuyển thiếu, chuyển bù được, server tự cấp khi đủ) **không** cảnh báo (QĐ-8);
  - 401/403 có thân JSON của PayOS tạo cảnh báo `payos_auth_failed` (checkout và đối soát, §4.3, §4.5);
  - đối soát PayOS **không** có cảnh báo `order_check_failed` (loại này chỉ dành cho cổng khác PayOS, hiện là Creem, §4.5): khi PayOS trả lỗi không đọc được (404, chữ ký phản hồi sai, dữ liệu lạ, HTTP 200 kèm `code` lỗi) chỉ có log `reconcile_failed` (mã đơn, lỗi), vì lỗi tạm của PayOS (quá thời gian lúc đọc thân, `code` lỗi kèm HTTP 200) ra giống dữ liệu hỏng và sẽ thành cảnh báo giả mỗi khi PayOS chậm. PayOS chỉ có thêm `order_payment_review` khi lệch tiền và `payos_auth_failed` ở trên.
  
  `payos.ts` chỉ thêm cờ `jsonBody` vào lỗi (QĐ-1: không thêm `redirect: "manual"`, không đổi timeout, để không đụng đường tiền đang chạy tốt). Hai lỗ có từ trước còn để lại (backlog): `fetch` của PayOS theo chuyển hướng (gửi tiếp header khóa), và thân JSON `null` ném `TypeError` (không phải `PaymentProviderError`: không có cảnh báo nào).
- Quy ước `amountPaid`: **phần tiền thuộc về giá, không gồm thuế**. PayOS không có thuế nên không đổi; Creem tính từ `amount_paid − tax_amount` (§4.2).

### 4.2 `CreemProvider` (`server/src/payment/creem.ts`, `creem-webhook.ts`, mới)

Theo khuôn `payos.ts`: `fetch` thuần, timeout 10 giây, `PaymentProviderError` có `httpStatus`, `unreachable` và `jsonBody`, không dùng SDK (chỉ ba lời gọi).

- **Gọi API (`call()`):** header `x-api-key`; `redirect: "manual"`: mọi 3xx thành `PaymentProviderError` có `httpStatus`, không theo và không đọc thân (`fetch` của Workers gửi tiếp `x-api-key` sang origin khác). Lỗi mạng hay quá thời gian chờ lúc nối, và quá thời gian chờ lúc đọc thân, là `unreachable`. Thân không đọc được thành JSON (vì lý do khác) là lỗi có `httpStatus`. HTTP lỗi: lỗi có `httpStatus`, `trace_id` của Creem (chỉ khi khớp `[A-Za-z0-9_-]{1,64}`) chép vào thông điệp, không chép nội dung lỗi gốc; `jsonBody` khi thân là đối tượng có `trace_id` dạng chuỗi. 2xx mà thân không phải đối tượng cũng là lỗi. Giá trị lạ chép vào thông điệp qua `show()`: chuỗi có `@` hay khoảng trắng ghi `[đã che]`, chuỗi khác cắt 32 ký tự.
- **Cấu hình:** `{ baseUrl, apiKey, webhookSecret?, productIds? }`; `sells` đúng khi có `productIds`.
  - Worker API dựng cổng bằng `creemFromEnv` (`deps.ts`): cần `CREEM_API_KEY` **và** `CREEM_WEBHOOK_SECRET` khác rỗng, thiếu một thì không có cổng `creem` (`POST /v1/webhooks/creem` trả 404). `CREEM_PRODUCT_IDS` đọc bằng `parseProductIds`: đúng ba mã gói, mỗi gói một mã `prod_[A-Za-z0-9_-]+`, ba mã khác nhau. Rỗng, điền dở hay trùng mã thì không có `productIds`: cổng chỉ **xử lý** đơn đã có (webhook, trạng thái, hoàn tiền, tranh chấp) mà không **bán** (`sells` false; §4.3). Nhờ vậy tắt bán thẻ khẩn cấp (rỗng ba mã rồi deploy Worker API) không làm mất webhook hoàn tiền hay đơn Creem đang chờ.
  - Worker admin dựng cổng chỉ đọc bằng `creemReaderFromEnv` (`admin-deps.ts`): chỉ `CREEM_BASE_URL` và `CREEM_API_KEY` (không secret webhook, không mã sản phẩm), kiểu trả về hẹp `Pick<PaymentProvider, "name" | "getPaymentStatus">` (đặt nhầm vào `Deps.payments` của Worker API thì `tsc` đỏ). `admin-deps.ts` giữ cả `adminPayments` và `realAdminDeps`; `deps.ts` dùng chung với Worker API nên không nhập `./admin*` (test `server/test/node/worker-split.test.mjs`).
- **`createCheckout`:** chỉ nhận `USD`; cần mã sản phẩm của gói; số tiền phải là số nguyên **100 tới 99 999 999** cent, kiểm **trước** khi gọi mạng. `POST {baseUrl}/v1/checkouts`, body
  `{ product_id: productIds[plan], request_id: String(orderCode), custom_price: amount, success_url: returnUrl, customer: { email }, metadata: { order_code, plan } }`.
  Kiểm response: `id` và `checkout_url` là chuỗi; `id` khớp `CHECKOUT_ID` (`^[A-Za-z0-9_-]{1,128}$`, `creem-webhook.ts`); `checkout_url` là `https`, **tên miền đúng `checkout.creem.io`**, không cổng lạ, không userinfo (không thì `PaymentProviderError`, để không bao giờ đưa URL lạ cho app). Trả `{ providerRef: id, checkoutUrl, qrCode: null }` với `checkoutUrl` ở dạng chuẩn hóa (`href` của WHATWG URL, như app phân tích lại).
- **`verifyWebhook`** (`verifyCreemWebhook`): secret rỗng (cổng chỉ đọc) thì `null`. Header `creem-signature` bắt buộc; tính HMAC-SHA256 dạng hex của thân thô với `webhookSecret`, so sánh thời gian cố định (`timingSafeEqual`, `crypto.ts`). Thiếu hay sai chữ ký thì `null` (route trả 400 và tạo cảnh báo `webhook_bad_signature`, như PayOS). Đúng chữ ký mà thân không phải JSON thì `"malformed"` (400, chỉ log). Sau đó:
  - thân không phải đối tượng hay thiếu `eventType` dạng chuỗi (Creem đổi định dạng): `unmatched` với `eventType` null;
  - loại sự kiện ngoài ba loại dưới: `ignore` và một dòng log `webhook_ignored`;
  - `checkout.completed`: `object.request_id` phải là chuỗi số nguyên dương viết bằng chữ số, không có số 0 đầu, an toàn; có thì `{ kind: "payment", orderCode, providerRef, reportUnknownOrder: { eventType, eventId } }` với `providerRef = object.id` khi khớp `CHECKOUT_ID` (không thì null). Thiếu hay sai `request_id` (khách trả qua link công khai, Storefront hay sản phẩm khác cùng tài khoản) là `unmatched`, không phải `"malformed"`;
  - `refund.created` và `dispute.created`: mã phiên lấy từ `object.checkout` (đối tượng có `id`, hay chính mã phiên dạng chuỗi), phải khớp `CHECKOUT_ID`; thiếu hay sai là `unmatched`. **`full`** đúng khi (tranh chấp, hay `object.status = "succeeded"` với hoàn tiền) **và** `object.transaction.refunded_amount`, `object.transaction.amount_paid` đều là số, `amount_paid > 0` và `refunded_amount ≥ amount_paid`; thiếu số nào thì `full = false`. Sự kiện mang thêm `eventId` (`id` của sự kiện, 1 tới 128 ký tự), hai số tiền của giao dịch, `refundStatus` (`object.status` của lần hoàn, tối đa 64 ký tự; null với tranh chấp) và `providerReason` (`object.reason`, tối đa 64 ký tự);
  - mọi mã đối tượng (`object.id`: `ch_…`, `ref_…`, `disp_…`) chỉ được dùng khi khớp `CHECKOUT_ID`: server không bao giờ hỏi Creem, lưu vào đơn hay tra đơn theo mã sai mẫu.
  - Hoàn tiền và tranh chấp **tin payload đã ký** (không hỏi lại API): payload có chữ ký HMAC nên không giả được khi không có secret; việc ta làm chỉ là ghi nhận, cảnh báo và chuyển đơn sang `refunded` (D5), không đụng license; và `status` của đơn trong OpenAPI của Creem chỉ liệt kê `pending` và `paid`, nên chưa chắc API phản ánh hoàn tiền (tài liệu: hỏi lại phiên sau khi hoàn vẫn thấy `paid`).
- **`getPaymentStatus`:** cần `providerRef` (thiếu hay chuỗi rỗng thì lỗi). `GET {baseUrl}/v1/checkouts?checkout_id={providerRef}`. Phản hồi phải đúng phiên đã hỏi: `id` bằng `providerRef`, `request_id` có mặt và bằng `String(orderCode)`, `order` vắng, `null` hay là đối tượng, `status` của phiên là `pending`, `processing`, `expired` hay `completed`; không thì `PaymentProviderError` (không cấp; đối soát cảnh báo `order_check_failed`, §4.5). Ánh xạ:

  | Phiên (`status`) | Đơn (`order`) | `PaymentStatus` |
  |---|---|---|
  | `completed` | `status` `paid` hay `partially_refunded`, `currency = "USD"`, mọi trường tiền đọc được, không có dấu hiệu giảm giá, phần trả thuộc về giá ≥ giá mong đợi (hay không có `amount_paid`) | `paid`; `amount = amountPaid = sub_total ?? amount` |
  | `completed` | như trên nhưng có dấu hiệu giảm giá, hay phần trả thuộc về giá < giá mong đợi | `underpaid` (giữ đơn); `amountPaid` = phần trả thuộc về giá kẹp trong [0, giá] (không có `amount_paid` thì 0); `reviewDetail` |
  | bất kỳ | `status` khác `pending` và `refunded` (gồm `paid`, `partially_refunded`, giá trị lạ, thiếu, `null`) mà dữ liệu hỏng: phiên không `completed`, `order.status` lạ, `order.currency` khác `"USD"` (kể cả `"usd"`), trường tiền có mặt mà không phải số nguyên ≥ 0 (`order.amount` bắt buộc; kể cả `custom_price` của phiên), `order.discount` không phải chuỗi, `discount` của phiên không phải chuỗi hay đối tượng | `underpaid` (giữ đơn); `amountPaid` 0; `amount` là giá đọc được đầu tiên (`sub_total`, rồi `amount`, không còn thì 0); `reviewDetail.provider_malformed_fields` (tên trường); log `creem_malformed_paid_session` (mã đơn, mã phiên, tên trường, không chép giá trị) |
  | `completed` | `refunded` | `refunded` (đơn đã trả rồi hoàn đủ trước khi ta cấp: không cấp) |
  | `completed` | `pending`, hay chưa có `order` | `processing` |
  | `pending`, `processing`, `expired` | chưa có `order`, `pending` hay `refunded` | như phiên |

  - **Giá** (QĐ-12): `net = sub_total ?? amount`, tức giá niêm yết **không gồm thuế** (OpenAPI cho thấy `amount` có thể gồm thuế: S1). `amount` trả về là `net`; `fulfilOrder` so nó với `orders.amount`. Chưa có đơn thì `amount` là `custom_price` của phiên (thiếu thì lỗi).
  - **Giá mong đợi:** `max(custom_price ?? net, net)`: `custom_price` Creem trả lại thấp hơn giá không nới phép so.
  - **Phần trả thuộc về giá:** `amount_paid − tax_amount` (thiếu `tax_amount` thì `amount_paid`). Trừ thuế thì một mã giảm giá nhỏ hơn thuế không lọt qua, và phép so đúng dù `amount` có gồm thuế hay không.
  - **Dấu hiệu giảm giá:** `order.discount` hay `discount` của phiên có mặt (không vắng, không `null`, không chuỗi rỗng), hay `order.discount_amount` có mặt và khác 0.
  - **`reviewDetail`** (`ReviewDetail`, `provider.ts`): `has_discount`, `provider_discount_amount`, `provider_amount_paid` (gồm thuế), `provider_tax_amount`, `provider_malformed_fields`; chỉ số và cờ, không chép mã giảm giá, email hay chữ nào của Creem. `fulfilOrder` chép nó vào `detail` của nhật ký (§4.4).
  - Ở phiên **có thể đã thu tiền**, dữ liệu tiền hỏng **không bao giờ** ném lỗi: ném lỗi thì đơn giữ `pending` rồi hết hạn sau 24 giờ mà không ai được báo; giữ đơn thì người vận hành được cảnh báo và cấp tay hay hoàn tiền. Ở phiên chưa thu tiền (hay đã hoàn) thì dữ liệu hỏng vẫn là lỗi (`order.currency` khác `"USD"`, `amount` hay `sub_total` sai kiểu, chưa có đơn mà thiếu `custom_price`).

  `paidAt` là `null` (Creem không báo thời điểm ở phiên); `paymentTime()` dùng lúc xử lý, kẹp trong hạn của đơn (QĐ33; hệ quả với khách trả muộn ở §4.4).
- **Lỗi xác thực** (401, 403 có thân JSON của Creem, `isProviderAuthFailure`): checkout trả `502 payment_provider_error` như hôm nay và tạo cảnh báo `creem_auth_failed`; đối soát cũng vậy (§4.5, §4.6). Creem trả 401 khi thiếu khóa, 403 khi khóa sai hay thiếu quyền (theo tài liệu; đo ở S11).

### 4.3 `GET /v1/plans` và `POST /v1/checkout` (`server/src/checkout.ts`)

- `POST /v1/checkout` nhận thêm `currency` tùy chọn: `"VND"` (mặc định khi thiếu) hay `"USD"`; giá trị khác thì `400 invalid_request` `field: currency`. Bảng cố định `SALES = { VND: { provider: "payos", ttl: 15 phút }, USD: { provider: "creem", ttl: 30 phút } }`; `SALE_CURRENCIES` là danh sách loại tiền của nó (thống kê Web Admin lấy từ đây, §4.6).
- **Luật "bán được loại tiền"** (`sellableCurrencies`), một luật cho cả `GET /v1/plans` lẫn `POST /v1/checkout`: cổng của loại tiền có mặt (Creem cần khóa API và secret webhook), cổng đang bán (`sells !== false`: Creem cần đủ ba mã sản phẩm), và **mọi** gói trong `PLANS` có giá loại tiền đó. Loại tiền không bán được thì `GET /v1/plans` không trả giá loại đó và `POST /v1/checkout` trả `503 pricing_not_configured`, kể cả khi app gửi thẳng.
- **Tương thích app cũ (≤ 0.1.9):** app cũ không gửi `currency` nên luôn đi PayOS/VND và vẫn nhận `qr_code` là chuỗi. Server **chỉ** trả `qr_code: null` cho đơn Creem, nghĩa là chỉ app mới (đã khai báo `currency: "USD"`) từng nhận. Cùng khuôn `?plans=` của gói 6 Months.
- Số tiền đơn = `plans[plan].prices[currency]`. Ước tính `license_expires_at` và `converted_days` dùng `computeGrant` theo loại tiền của đơn (bảng đã có đủ hai loại tiền).
- Hạn của link theo cổng (`ttl` trong `SALES`): PayOS 15 phút (như cũ), Creem 30 phút (`CREEM_CHECKOUT_TTL_SECONDS`, D7). `orders.expires_at` = hạn này (dùng cho `paymentTime()` và cho app). Server **không gửi** hạn cho Creem (tài liệu đã tải không có tham số hạn phiên); phiên Creem có thể sống lâu hơn (S6, chưa đo).
- Response thêm `provider` (`"payos"` hay `"creem"`); `qr_code` là `null` với Creem. `returnUrl` của Creem là `/v1/pay/return` có sẵn (Creem thêm tham số vào URL, trang bỏ qua); Creem không có URL hủy.
- Cổng lỗi lúc tạo phiên: đơn thành `failed`, log `checkout_failed`, trả `502 payment_provider_error`. Khóa API bị từ chối (`isProviderAuthFailure`) thì thêm cảnh báo theo cổng (`payos_auth_failed`, `creem_auth_failed`); lỗi ghi cảnh báo chỉ vào log (`checkout_alert_failed`), **không bao giờ đổi phản hồi** trả khách (luôn 502).
- `GET /v1/plans` giữ nguyên danh sách gói và logic `?plans=`; `prices` chỉ có các loại tiền bán được (Creem chưa bán thì app không thấy USD; app cũ chỉ đọc `prices.VND`); **thêm trường `suggested_currency`**: `"USD"` khi bán được USD và nước của request (`request.cf.country`, thiếu thì header `CF-IPCountry`) khác `VN` và `XX`; ngược lại (Việt Nam, không đọc được nước, hay không bán được USD) là `"VND"`.

### 4.4 Webhook (`server/src/orders.ts`, route `/v1/webhooks/:provider`)

**Route.** Đọc **thân thô** (`c.req.text()`), dựng `WebhookRequest`, gọi `verifyWebhook`, rồi theo kết quả:

| Trường hợp | Phản hồi | Dấu vết |
|---|---|---|
| Thân quá 16 KiB (`bodyLimit` của `/v1/*`) | `413 invalid_request` | log `webhook_too_large` |
| Không đọc được thân (bên gửi ngắt giữa chừng) | `400 invalid_request` | log `webhook_body_unreadable` |
| `"malformed"` | `400 invalid_request` | log `webhook_malformed`; không cảnh báo, không ghi D1 |
| `null` (thiếu, sai chữ ký, thiếu secret) | `400 invalid_signature` | log và cảnh báo `webhook_bad_signature` (lỗi ghi cảnh báo không đổi phản hồi, log `webhook_alert_failed`) |
| `ignore` | `200 {ok:true, result:"ignored"}` | (Creem: log `webhook_ignored`) |
| `unmatched` | `200 {ok:true, result:"unmatched"}`, hay `"duplicate"` khi cùng mã sự kiện đã ghi | `recordUnmatched`; D1 lỗi thì `503` (cổng gửi lại), log `webhook_unmatched_failed` |
| `refund` | `200 {ok:true, result}` với `result` là `RefundResult` | `handleRefund`; lỗi thì `503`, log `webhook_refund_failed` |
| `payment` | `200 {ok:true, result}` với `result` là `FulfilResult` | `fulfilOrder`; mã đơn không có trong D1 (`unknown_order`) mà cổng đặt `reportUnknownOrder` (Creem) thì cũng `recordUnmatched` (PayOS không đặt: mẫu confirm-webhook mang `orderCode` lạ, chỉ trả 200); lỗi thì `503`, log `webhook_fulfil_failed` |

`kind: "payment"` vẫn **`await`** và trả `503` khi lỗi tạm: Creem thử lại 5 lần trong 24 giờ (30 giây, 5 phút, 30 phút, 6 giờ), chỉ HTTP 200 là thành công, và tài liệu không nói endpoint bị tắt vì lỗi liên tiếp. Cron đối soát vẫn là lưới thứ hai cho thanh toán (không cho hoàn tiền).

**Sự kiện không khớp đơn (`recordUnmatched`, QĐ-7).** Webhook đúng chữ ký mà không chỉ ra đơn nào của ta (`unmatched`; hoàn tiền hay tranh chấp mà không đơn nào mang mã phiên đó; cò cấp của Creem với mã đơn lạ): khách có thể đã trả tiền mà server không biết. Ghi một nhật ký `payment_unmatched` không gắn đơn (`order_code` NULL; `detail`: `provider`, `event_type` hay null, `provider_ref`, `event_id`), một cảnh báo `payment_unmatched` và một dòng log, trong cùng một batch; khử trùng theo (`event_id`, `provider`): gửi lại cùng mã không ghi thêm. Thiếu mã sự kiện thì mỗi lần gửi là một sự kiện. Không cấp key nào; người vận hành tra mã ở dashboard Creem rồi tạo license tay hay hoàn tiền.

**Hoàn tiền và tranh chấp (`handleRefund`, viết lại theo Q1 ngày 2026-10-15).** Tra đơn theo `(provider, provider_ref)`; không có thì log `refund_unknown_order`, `recordUnmatched` và trả `unknown_order`. Có thì **tin payload đã ký** (§4.2), không hỏi lại API, **không đụng license** (D5):

- Mỗi sự kiện chưa thấy của một đơn đã biết, **ở bất kỳ trạng thái nào**, để lại đúng một nhật ký, một cảnh báo (cùng tên) và một dòng log `order_refund_event`:
  - tranh chấp: `order_disputed`, **luôn**, kể cả đơn đã `refunded`;
  - hoàn tiền `succeeded` và `full`: `order_refunded`;
  - hoàn tiền `succeeded` mà không đủ (hoàn một phần, hay payload thiếu số): `order_partially_refunded`;
  - lần hoàn chưa thành công (`status` khác `succeeded`: đang chờ, thất bại, thiếu): `order_refund_unconfirmed`.
- `full` mà đơn chưa `refunded` (`pending`, `processing`, `underpaid`, `failed`, `expired`, `cancelled`, `paid`, `paid_needs_review`) thì đơn thành **`refunded`**, kể cả đơn chưa cấp (webhook hoàn tiền tới trước khi cấp). `refunded` thuộc `SETTLED_STATUSES`, nên sau đó webhook, đối soát, cấp tay (`/grant`) và `/resolve` đều từ chối đơn này: **không bao giờ cấp hay gửi key nữa**. Không `full` thì trạng thái đơn giữ nguyên (đơn `paid` hoàn một phần vẫn `paid`).
- **Khử trùng theo mã sự kiện** (`event_id` trong `detail`): một batch gồm câu đổi trạng thái và câu ghi nhật ký, cả hai chỉ có tác dụng khi nhật ký của đơn chưa có dòng nào mang mã sự kiện này, rồi cảnh báo chỉ ghi khi câu ghi nhật ký vừa có tác dụng. Creem gửi lại hay hai request chạy chồng: chỉ một lần có tác dụng (`duplicate`). Thiếu mã sự kiện thì không khử trùng được.
- `detail`: `event_id`, `reason`, `provider_reason`, `refund_status`, `full`, `refunded_amount`, `provider_amount_paid`, `prev_status`, `plan`, `amount`, `currency`, `license_id`. Cột `audit_log.license_id` là `license_id` của đơn, thiếu thì `renew_license_id` (đọc ngay trong câu ghi), để trang license ở Web Admin thấy sự kiện.
- `RefundResult`: `refunded` (sự kiện này đổi đơn sang `refunded`), `noted` (chỉ nhật ký và cảnh báo), `duplicate`, `unknown_order`.
- Thư cảnh báo không mang mã đơn (gộp theo loại): thư chỉ cách tìm (lọc nhật ký ở Web Admin theo hành động) và gợi ý rút ngắn hạn hay thu hồi (§4.6).

**Cấp license (`fulfilOrder`)**, dùng chung cho webhook và đối soát:

- Truyền `orders.provider_ref` vào `getPaymentStatus`. Đơn chưa có `provider_ref` (Worker dừng giữa lúc tạo phiên và lúc lưu) mà webhook đã ký của **đúng cổng của đơn** mang mã phiên: hỏi Creem theo mã đó; Creem xác nhận đúng đơn (`request_id`) thì mới lưu `provider_ref` (**sau** khi `GET` xác nhận, có điều kiện `provider_ref IS NULL`, log `order_provider_ref_filled`).
- Cấp khi cổng báo `paid`, `amount` của cổng **bằng** `orders.amount` và `amountPaid ≥ amount`. Với Creem `amount` là `sub_total ?? amount` (giá niêm yết, **không gồm thuế**) và `amountPaid` là phần trả thuộc về giá, cũng không gồm thuế (§4.2). Đơn có dấu hiệu giảm giá hay trả thấp hơn giá không bao giờ đến đây với `paid` (Q4).
- Cổng báo `refunded`: đơn thành `refunded` (xét **trước** lệch số tiền), nhật ký `order_refunded` (`detail.source = "provider_status"`, không có `event_id`) và cảnh báo `order_refunded`, như webhook hoàn đủ (Q1).
- Số tiền của cổng khác số tiền của đơn (mọi cổng): đơn `failed`, nhật ký `order_amount_mismatch`, cảnh báo `order_payment_review`, log `order_amount_mismatch`. Cổng báo `paid` mà thiếu tiền, hay báo `underpaid` (Creem giữ đơn): đơn `underpaid`, nhật ký `order_underpaid`, cảnh báo `order_payment_review` ở mọi cổng **trừ PayOS** (QĐ-8). `detail` của hai nhật ký: `amount`, `currency`, `provider_amount`, `amount_paid`, cộng `reviewDetail` của cổng nếu có (`has_discount`, `provider_discount_amount`, `provider_amount_paid`, `provider_tax_amount`, `provider_malformed_fields`).
- **Chỉ khi đổi thật:** câu đổi trạng thái có điều kiện trong SQL (`status <> ? OR amount_paid <> ?`, cùng điều kiện chưa khép), nhật ký chỉ ghi khi câu đó có tác dụng, cảnh báo chỉ khi nhật ký vừa ghi, cả ba trong một batch. Webhook gửi lại, đối soát hỏi lại hay hai request chạy chồng: đúng một nhật ký và một cảnh báo.
- Trạng thái khác (`pending`, `processing`, `expired`, `cancelled`…) chỉ ghi trạng thái và lúc hỏi.
- `orders.amount_paid` của đơn Creem là số **không gồm thuế**, để doanh thu không cộng thuế.
- **Khách trả muộn:** `paymentTime() = min(max(paidAt ?? now, created_at), expires_at, now)`. Creem không báo `paidAt`, nên thời điểm tính gói là `min(lúc xử lý, expires_at)`. Khách trả sau giờ hẹn (30 phút) mà đơn còn được xử lý (đối soát hỏi tới 24 giờ; webhook tới sau đó vẫn cấp được vì `expired` không thuộc `SETTLED_STATUSES`) vẫn được cấp, nhưng `cycle_anchor` và hạn license tính từ `expires_at` của đơn: **khách mất đoạn trễ** từ `expires_at` tới lúc trả (server không biết lúc trả, chỉ biết lúc xử lý; ở đường đối soát đoạn này tới khoảng 24 giờ). Cùng cách tính với PayOS. Chờ S6 (hạn sống phiên) và S5; chủ dự án quyết nếu muốn đổi (ví dụ không kẹp khi cổng không báo giờ, hay đọc giờ trả của Creem nếu có: mục 11).
- Không thêm trạng thái đơn mới: `refunded` đã có trong `SETTLED_STATUSES`; nay nghĩa rộng hơn (cổng báo hoàn đủ ở bất kỳ trạng thái nào, kể cả trước khi cấp).

### 4.5 Đối soát và hết hạn (`server/src/reconcile.ts`)

`reconcile.ts` đã chạy theo `orders.provider` và **có sửa** trong đợt này (bản 2026-10-14 ghi "giữ nguyên": không còn đúng):

- Mỗi lượt cron (5 phút) hỏi tối đa 50 đơn `pending`, `processing` hay `underpaid` tạo trong 24 giờ: giờ đầu mỗi lượt, sau đó khoảng mỗi giờ. Đơn `underpaid` được hỏi lại (PayOS: khách chuyển bù; Creem: Creem trả dữ liệu đúng sau đó thì tự cấp). Với Creem mỗi lần hỏi là một lời gọi. Hạn mức API của Creem chưa rõ (chỉ biết có `429`): đối soát dừng đợt khi gặp 429 hay 3 lần liên tiếp 5xx hoặc không liên lạc được.
- Lỗi ở một đơn: log `reconcile_failed` (mã đơn, lỗi), ghi lúc hỏi, rồi cảnh báo theo loại lỗi (mỗi đơn lỗi một lần đếm; lỗi ghi cảnh báo chỉ vào log `reconcile_alert_failed`, đối soát hỏi tiếp các đơn còn lại):
  - khóa API bị từ chối (`isProviderAuthFailure`): `payos_auth_failed` hay `creem_auth_failed` theo cổng của đơn (đơn cũ có thể đã được khách trả: thư nói mốc 24 giờ);
  - không đọc được trạng thái đơn (`PaymentProviderError` không `unreachable` mà không có mã HTTP, có mã dưới 400 (3xx, 2xx thân không dùng được), hay 404), **chỉ với đơn của cổng khác PayOS (hiện là Creem) mà đơn đã có `provider_ref`** (`checkFailedAlert`): `order_check_failed`. Hỏi lại không tự khỏi, mà đơn khách đã trả sẽ thành `expired` sau 24 giờ. Đơn PayOS không có cảnh báo này (lỗi tạm của PayOS, như quá thời gian lúc đọc thân hay `code` lỗi kèm HTTP 200, ra giống dữ liệu hỏng và sẽ thành cảnh báo giả mỗi khi PayOS chậm): chỉ log `reconcile_failed`, cùng cảnh báo khóa `payos_auth_failed` ở trên. Đơn chưa có `provider_ref` (tạo phiên lỗi, không có gì để đọc) cũng chỉ có log;
  - 5xx, 429, 400, lỗi mạng, quá thời gian chờ, 401/403 không có thân của cổng, lỗi không phải của cổng (D1): không cảnh báo.
- `expire_orders`: đơn `pending` hay `processing` tạo quá 24 giờ thành `expired`. Đơn `underpaid` **không** bị đụng (đơn Creem bị giữ chờ người vận hành).

### 4.6 Cảnh báo, nhật ký, admin

- **Loại cảnh báo** (`alerts.ts`) thêm: `order_payment_review`, `order_refunded`, `order_partially_refunded`, `order_refund_unconfirmed`, `order_disputed`, `payment_unmatched`, `payos_auth_failed`, `creem_auth_failed`, `order_check_failed`. Cùng cơ chế gom theo cửa sổ một giờ và email người vận hành như các loại có sẵn. Thư không mang mã đơn: thư của các loại gắn nhật ký chỉ cách tìm (lọc nhật ký ở Web Admin theo hành động `order_refunded`, `order_amount_mismatch`, `order_underpaid`, `payment_unmatched`…); thư khóa API nói đặt lại khóa nào cho cả hai Worker.
- **Trạng thái đơn ở cổng** (`admin.ts`, `/admin/orders/:orderCode/payment-status`): truyền `providerRef` của đơn vào `getPaymentStatus`. Worker admin có cổng `creem` **chỉ đọc** (`creemReaderFromEnv`, `admin-deps.ts`, §4.2); `AdminDeps.payments` chỉ cần `getPaymentStatus`; `AdminEnv` thêm `CREEM_BASE_URL`, `CREEM_API_KEY`. `CREEM_API_KEY` nằm trong `secrets.required` của Worker admin (§4.7), nên thiếu secret thì `wrangler deploy` dừng; chỉ khi khóa bị xóa hay đặt rỗng sau deploy thì không có cổng `creem` và đơn Creem trả `502` "không có cổng creem" kèm log `admin_no_gateway` (hai câu cũ của §4.6 và §4.7 về chỗ này nay khớp nhau). Worker admin **giữ** `CREEM_API_KEY` ở v1 (QĐ-2) và **không** giữ `CREEM_WEBHOOK_SECRET` (test Node cấm cả trong `vars` lẫn `secrets.required`). Trạng thái Creem báo có thể vẫn là `paid` sau khi hoàn (hoàn tiền nằm ở giao dịch).
- **Thống kê theo loại tiền.** `/admin/stats` nhận `?currency=VND|USD` (mặc định `VND`, giá trị khác thì 400 `invalid_request` `field: currency`); các câu SQL doanh thu và các câu đếm đơn đi kèm doanh thu (`money.*`, `customers.grants_30d`, `customers.grants_monthly`) thêm `AND currency = ?`. Phản hồi có `currency` (`"VND" | "USD"`) và `currencies`: `VND` luôn có, loại khác khi có đơn loại đó với `amount_paid > 0` (mọi trạng thái) hay trạng thái `paid`, `paid_needs_review`, `refunded` (đơn cấp tay với `amount_paid = 0` vẫn làm nút USD hiện). `ORDER_CURRENCIES` (`admin-read.ts`) **là** `SALE_CURRENCIES` của `checkout.ts` (một nguồn). Đơn 30 ngày theo trạng thái, email key, máy, license và dùng thử không phụ thuộc loại tiền. `/admin/summary`: `revenue_today` thành `{ VND, USD }` (bỏ `currency`).
- **Nghĩa của doanh thu:** tổng `amount_paid` của đơn `paid`. Doanh thu USD là giá niêm yết **không gồm thuế, chưa trừ phí Creem**. Đơn hoàn đủ (`refunded`) ra khỏi doanh thu của ngày đã trả; hoàn một phần vẫn tính đủ (đơn giữ `paid`); cấp tay một đơn kẹt ghi `amount_paid` đang có của đơn (có thể 0).
- **Web Admin hiển thị:** `fmtMoney(n, currency)` (`format.ts`, cùng kiểu `fmtVnd`, không dùng `Intl.NumberFormat`: VND `500.000 đ`, USD từ cent `$3,99`; thiếu loại tiền thì coi là VND), nút VND | USD ở trang Tổng quan khi `currencies` có hơn một loại, số tiền của đơn theo loại tiền của đơn, tên cổng và lời dẫn theo `orders.provider`. Đơn Creem `underpaid` có nhãn "Trả thấp hơn giá" (không dùng "chuyển thiếu", chỉ đúng với VietQR) và thẻ giải thích theo `detail` của nhật ký (mã giảm giá, số Creem báo, trường hỏng); nhóm hàng đợi "Trả thiếu hay cần xem số tiền (30 ngày)". Nhật ký có tên tiếng Việt cho các hành động mới (`order_refunded`, `order_partially_refunded`, `order_refund_unconfirmed`, `order_disputed`, `payment_unmatched`, `license_shortened_manually`…). Trang Nhật ký đọc `?action=` làm bộ lọc ban đầu; cảnh báo hoàn tiền, tranh chấp và `payment_unmatched` ở trang Việc cần xử lý có lối "Xem nhật ký" tới đó.
- **Thẻ hoàn tiền theo loại đơn** (`OrderPage.tsx`, hàm thuần ở `refund-kit.ts`). `orderGrantEffect` đọc nhật ký của đơn: dòng cấp (`license_issued`, `license_extended`, `license_plan_changed`: đơn đã cộng bao nhiêu ngày vào license nào, hạn trước và sau đơn) và các lần `license_shortened_manually` kèm mã đơn. `refundCase` chọn thẻ cho đơn `refunded`: (1) chưa áp vào license nào: không cần làm gì; (2) đã rút đủ số ngày của đơn (nhắc kiểm nếu license được cộng thêm sau đó); (3) gia hạn, hay mua mới mà license còn đơn đã trả khác: **rút đúng phần của đơn, đừng thu hồi**; (4) mua mới và license chỉ gồm đơn này: thu hồi hay rút ngắn, người vận hành quyết; (5) đổi gói: Web Admin không đổi lại gói, rút ngắn tự chọn số ngày; (6) license đã thu hồi, hết hạn hay không có. Đơn chưa `refunded` mà nhật ký có hoàn một phần, tranh chấp hay hoàn chưa thành công thì có thẻ cảnh báo riêng. Nút "Ghi đã hoàn tiền" (`/admin/orders/:n/resolve`, `action: "refunded"`) vẫn chỉ cho đơn `paid_needs_review`; với đơn Creem đó là bước dự phòng khi webhook hoàn đủ tới trễ hay mất (webhook hoàn đủ tự chuyển đơn sang `refunded`).
- **Rút ngắn hạn** (Q2), `POST /admin/licenses/:id/shorten` (`admin.ts`):
  - request JSON: `note` (bắt buộc, 1 tới 500 ký tự sau khi bỏ khoảng trắng hai đầu), `days` (số nguyên 1 tới 3650), `expected_expires_at` (**bắt buộc**, số nguyên dương: hạn mà giao diện đang hiển thị), `order_code` (tùy chọn, vắng hay `null`; có thì là số nguyên dương và phải là đơn của license: `license_id` hay `renew_license_id`);
  - thứ tự kiểm: `400 invalid_request` kèm `field` (`note`, rồi `days`, `expected_expires_at`, `order_code` sai hình dạng) → `404 not_found` → `400` `field: order_code` (đơn không thuộc license) → câu ghi → nếu câu ghi không có tác dụng: `409 license_revoked` → `409 conflict` (hạn hiện tại khác `expected_expires_at`) → `409 too_far {max_days, expires_at}` (hạn mới không sau bây giờ; `max_days = max(0, floor((expires_at − now − 1) / 86400))`, không kẹp 3650) → `409 conflict` (license đổi giữa lúc đọc và lúc ghi);
  - câu ghi: `UPDATE licenses SET expires_at = expires_at − days × 86400, version = version + 1` với điều kiện đúng `id`, đúng `version` đã đọc, **`AND expires_at = expected_expires_at`**, chưa thu hồi, hạn mới sau bây giờ; cùng batch là nhật ký `license_shortened_manually` (`detail`: `days`, `from_expires_at`, `expires_at`, `order_code`, `note`; cột `order_code` là mã đơn nếu có), chỉ ghi khi câu ghi có tác dụng. `200 {license_id, expires_at}`. Phản hồi 409 không ghi nhật ký. Gửi lại cùng `expected_expires_at` sau khi lần trước đã áp (bấm hai lần, mạng lỗi) là `409 conflict`, không trừ hai lần. Giữ gói, `cycle_anchor`, `anchor_applied_at` và activation;
  - hộp "Rút ngắn hạn…" (`ShortenDialog.tsx`), mở từ trang đơn (điền sẵn số ngày còn lại của đơn, gửi `order_code`) hay trang license (tự chọn số ngày, không mã đơn; chữ nhắc rút phần của một đơn đã hoàn thì làm từ trang đơn): chốt hạn lúc mở hộp và gửi làm `expected_expires_at`; số ngày tối đa tính như server (`maxShortenDays`, kẹp 3650); lý do bắt buộc và gõ `RUT NGAN` để xác nhận; `409 conflict` đóng hộp và trang tải lại; lỗi không rõ kết quả (mất kết nối, 5xx) khóa nút gửi tới khi đóng hộp;
  - lưu ý nghiệp vụ (hộp và runbook nói): token đang có giữ hạn cũ tới lần làm mới kế tiếp (mỗi 24 giờ; máy offline tới 14 ngày, `refresh_before`); hạn ngắn lại có thể làm hạn mức của chu kỳ cuối nhỏ đi ngay (chu kỳ cuối tính theo số ngày còn lại); đơn đổi gói bị hoàn thì rút ngắn không đổi lại gói, khách giữ gói mới; EULA chỉ cho rút ngắn hay thu hồi khi đơn được hoàn tiền (mục 6), nên rút không kèm mã đơn phải ghi lý do.
- `/admin/lookup` vẫn trả `provider_ref` của đơn (`SELECT *`, chỉ bỏ `order_token_hash`; chỉ admin, có từ trước); danh sách đơn (`ORDER_COLUMNS`) không trả cột này.
- Nút "xác nhận webhook" (`/admin/payos/confirm-webhook`) vẫn chỉ cho PayOS; webhook Creem tạo ở dashboard Creem (mục 7).

### 4.7 Cấu hình (`server/wrangler.jsonc`, `wrangler.admin.jsonc`, `src/env.ts`)

Secret webhook đặt sai (giá trị giữ chỗ) thì mọi webhook Creem trả 400 và cảnh báo `webhook_bad_signature`; khóa hay secret bị xóa hay đặt rỗng sau deploy thì Worker API không dựng cổng `creem` (webhook 404; đối soát mỗi đơn Creem đang chờ chỉ ghi log `reconcile_failed`, không có cảnh báo).

- Một test khóa **tỉ lệ giá mỗi ngày** (so với Monthly) của bảng USD so với bảng VND trong sai số **3%** (bộ giá D2 lệch 2,4% ở 6 Months); chống sửa một bảng mà quên bảng kia.

| # | Cần đo | Giả định hiện tại | Nếu khác |
|---|---|---|---|
| S1 | Với `tax_mode: exclusive`: `order.amount` có gồm thuế không; `sub_total`, `tax_amount`, `amount_paid` có ở `GET /v1/checkouts` không (SP1) | Mã đọc giá là `sub_total ?? amount` (QĐ-12) và phần trả thuộc về giá là `amount_paid − tax_amount` (§4.2), nên đúng dù `amount` gồm thuế hay không, **miễn có `sub_total`**. Tài liệu: ví dụ `amount` 1000, `amount_paid` 1210 (thuế 210) là của **giao dịch** (`transaction` trong payload `refund.created`), không phải của đơn; mẫu OpenAPI `OrderEntity` có `amount` 2000 = `sub_total` 1800 + `tax_amount` 200 (mô tả "total amount"), `amount_paid` 1900 sau `discount_amount` 100: nghi `amount` của đơn **gồm thuế** | Thiếu `sub_total` mà `amount` gồm thuế: giá cổng báo khác giá đơn, đơn `failed` + `order_amount_mismatch` + cảnh báo (không cấp sai, nhưng mọi đơn có thuế phải cấp tay): đọc giá từ `custom_price` khi thiếu `sub_total`, sửa bộ giả lập và test |

Đơn đã trả không bị ảnh hưởng: nhánh đã trả đọc giá từ `order` và không đòi `custom_price`. Tài liệu Creem nói trường này chỉ có khi tạo với `custom_price`, nên dự kiến có. ## 12. Thay đổi sau hardening (2026-10-15/16)

So với bản chủ dự án duyệt ngày 2026-10-14. Nguồn: backlog `docs/superpowers/plans/2026-10-14-creem-06-hardening-backlog.md` và quyết định của chủ dự án ngày 2026-10-15. Mã ở cây làm việc nhánh `payment`, chưa commit.

**Quyết định của chủ dự án (2026-10-15):**
- **Q1, hoàn tiền (§4.4):** hoàn đủ một đơn chưa `refunded` ở **bất kỳ** trạng thái nào thì đơn thành `refunded` và không bao giờ cấp hay gửi key nữa (bản cũ: chỉ đơn `paid`, đơn chưa trả thì bỏ qua). Mọi sự kiện hoàn tiền hay tranh chấp của đơn đã biết có nhật ký, cảnh báo và log; tranh chấp luôn cảnh báo, kể cả đơn đã `refunded`; khử trùng theo mã sự kiện; thêm `order_refund_unconfirmed` cho lần hoàn chưa thành công.
- **Q2, rút ngắn hạn (§4.6):** Web Admin có thao tác rút ngắn hạn license (trừ số ngày, không xuống tới bây giờ, kiểm hạn đang hiển thị, nhật ký, gõ xác nhận); thẻ hoàn tiền theo loại đơn không mời thu hồi khi license còn thời gian khách đã trả ở đơn khác; EULA và website nói license có thể bị rút ngắn hạn hay thu hồi khi đơn được hoàn tiền.
- **Q3, đơn thẻ trả muộn (§5):** app không báo thất bại sớm; hỏi tiếp tới 24 giờ sau hạn (nhịp 5 giây, 30 giây, 120 giây); chữ của đơn thẻ quá giờ hay không thành dặn "nếu đã trả, key sẽ gửi qua email; đừng trả lại".
- **Q4, giảm giá (D6, §4.2):** không tạo mã giảm giá; mã không cấp tự động đơn Creem có dấu hiệu giảm giá hay trả thấp hơn giá, mà giữ đơn và cảnh báo `order_payment_review`.
- **Điều khoản Creem 3.7:** câu "Creem là bên bán lại (merchant of record)" ở EULA 1.3, chính sách 1.2, website và màn hình thẻ trong app (năm ngôn ngữ).

**Quyết định kỹ thuật trong đợt:** QĐ-1 không đổi đường gọi API của PayOS (chỉ thêm cờ `jsonBody`); QĐ-2 Worker admin giữ `CREEM_API_KEY` ở v1, không giữ secret webhook; QĐ-5 câu đồng ý riêng cho thẻ; QĐ-6 mục gập EULA khi chọn thẻ; QĐ-7 sự kiện không khớp đơn có nhật ký và cảnh báo (`payment_unmatched`); QĐ-8 PayOS `underpaid` không cảnh báo; QĐ-12 giá Creem là `sub_total ?? amount`.

**Phòng thủ giữ đơn (Creem, §4.2):** phiên có thể đã thu tiền mà dữ liệu mâu thuẫn hay hỏng (phiên chưa `completed` mà đơn đã trả, `order.status` lạ, loại tiền khác USD, trường tiền sai kiểu) không còn ném lỗi (đơn hết hạn im lặng) mà giữ đơn `underpaid` với cảnh báo; phần trả tính không gồm thuế và kẹp trong [0, giá]; `call()` không theo chuyển hướng, phân biệt quá thời gian lúc đọc thân, kiểm thân và mã phiên.

**Cảnh báo mới:** `order_payment_review` (lệch tiền ở mọi cổng, giữ đơn ở cổng khác PayOS), `order_refund_unconfirmed`, `payment_unmatched`, `order_check_failed` (đối soát không đọc được đơn Creem đã có `provider_ref`; không áp cho PayOS), `payos_auth_failed` và `creem_auth_failed` (thay loại cảnh báo khóa API chung của bản cũ; chỉ khi 401/403 có thân JSON của chính cổng).

**Lệch so với chữ của bản cũ:** PayOS có thêm cảnh báo (§4.1); `reconcile.ts` có sửa (§4.5); cấu hình Creem có hai vai xử lý và bán (`sells`, `CREEM_PRODUCT_IDS` rỗng là tắt bán); `SALES` thay `PROVIDER_BY_CURRENCY`; mở trình duyệt ở `license/app.rs` thay vì `purchase::start`; `PlansReply` thay `PlansBody`; `priceUsdCents` thay `priceUsd`; runbook phần Creem là mục 9.

**Hành vi cần chủ dự án biết:** khách trả sau giờ hẹn 30 phút vẫn được cấp nhưng hạn gói tính từ giờ hẹn (mất đoạn trễ, §4.4); rút ngắn hạn không có hiệu lực trên máy khách tới lần làm mới token kế tiếp (tới 24 giờ, máy offline tới 14 ngày).
